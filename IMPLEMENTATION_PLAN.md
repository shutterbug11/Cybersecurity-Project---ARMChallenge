# On-Device AI Cybersecurity Assistant — Implementation Plan

**Status:** Planning only, 7 November 2026. No Android code, model conversion, dependency installation, or implementation work is authorized by this document. Companion design: [`SYSTEM_ARCHITECTURE.md`](SYSTEM_ARCHITECTURE.md).

## 1. Executive project summary

Build a native, offline-first Android assistant for Arm phones. The first end-to-end release path is **manual URL and pasted/shared SMS classification → evidence and rule-based remediation → Room history → optional local Llama explanation**. Network monitoring and file malware analysis are separately gated because the current repository does not yet supply deployable artifacts or reproducible mobile input pipelines for them. Every verdict identifies its model and limits. The app does not claim continuous or complete device protection.

The audited source is the local workspace copy of [`Cybersecurity-Project---ARMChallenge`](https://github.com/shutterbug11/Cybersecurity-Project---ARMChallenge), currently at the prior uploaded repository content. The workspace also has **untracked-by-Git, local-only** CSV datasets, phishing/SMS pickle artifacts, image data, and archive chunks. These are audit inputs but cannot be assumed available to a clean GitHub checkout. The repository contains the new CNN `.pt` and performance `.pkl` under `Malware Detection using CNN/malware_cnn-main/results/`.

## 2. Audit method and evidence boundaries

Inspected all six notebooks, `train_cnn.py`, the saved CNN checkpoint/performance pickle, local dataset headers, and the local phishing/SMS pickle object metadata. The pickle files report scikit-learn 1.5.1 provenance and issued version mismatch warnings when inspected with local scikit-learn 1.8.0. Original notebook outputs are **historical notebook results**, not reproduced results. No Android conversion, operator validation, device benchmark, probability calibration, or network feature-parity test has been done. Local pickle files must be treated as potentially unsafe executable serialization and processed only as trusted build inputs in a controlled environment.

### Folder-by-folder findings

1. **`Cybersecurity_Intution`** — `Basic_walkthrough.ipynb` performs exploratory network attack analysis, cleaning, port joining, correlations, and charts. It imports pandas, NumPy, SciPy, Matplotlib, Seaborn, and `missingno`; local data includes `Cybersecurity_attacks.csv` and `TCP-ports.csv`. It is **not a trained detector**: no input tensor, output label contract, checkpoint, or metrics. The notebook references CSV names without the local `data/` prefix and includes source/destination IPs, ports, protocol, attack category, timestamps, and duration derivation. Use as domain research for indicators only, never as an inference model.
2. **`DDos Attack Classifier`** — `main_file.ipynb` reads local `data/DDos.csv` (79 columns: 78 flow features plus `Label`), strips column whitespace, drops null rows, maps `BENIGN→0`, `DDoS→1`, and uses a 70/30 random row split (`random_state=42`). It trains RandomForest (`n_estimators=50`), LogisticRegression, and `MLPClassifier(hidden_layer_sizes=(10,), max_iter=10)`, then computes accuracy/F1/precision/recall/ROC. Stored notebook output reports RF accuracy **0.9995**, F1 **0.9995**, precision **1.0000**, recall **0.9990**; MLP accuracy **0.9827**. Logistic regression and MLP show convergence warnings. No fitted model, scaler, feature-order manifest, CICFlowMeter implementation, or export exists. `StandardScaler` is imported but not applied. The CSV includes a duplicate `Fwd Header Length.1` column name generated by pandas. Row-random evaluation may overstate generalization to unseen networks/attack sessions. **Not deployable.** Dependencies: pandas, NumPy, scikit-learn, Matplotlib, Seaborn.
3. **`Malware Detection`** — `malware detection and classification.ipynb` trains on local pipe-delimited `Data/MalwareData.csv`: 57 columns (`Name`, `md5`, `legitimate`, and **54 numeric Windows PE features**). It removes `Name`/`md5`, splits 80/20 randomly, trains shallow RandomForest (`max_depth=2`), LogisticRegression, and a Keras dense network `54→16→8→4→1 sigmoid`. `legitimate=1`, malware=0 based on dataset examples and notebook label. Stored RF test accuracy **0.98381**, F1 **0.97309**; logistic test accuracy **0.69721**, F1 **0** with convergence warning; Keras test accuracy **0.95382**, F1 **0.91974**. The Keras confusion matrix shown in the notebook is `[[19030,220],[1055,7305]]`. No fitted artifacts or PE feature extraction code exist. An absolute Windows training path is stale. This analyzes Windows PE static features, **not Android APKs or live behavior**. Dependencies: pandas, NumPy, scikit-learn, TensorFlow/Keras, Matplotlib. **Not deployable.**
4. **`Malware Detection using CNN`** — Original Colab notebook `Malware_Detection_with_CNN.ipynb` defines a 3-channel PyTorch CNN with five convolutions/pooling steps and `[N,3,256,256]` RGB-normalized input, but has no saved weights. Its Colab paths, shell commands, and TensorBoard loops are not an independent mobile pipeline. The later local `train_cnn.py` is a **different trained architecture**: `Conv(1,8)→Conv(8,16)→Conv(16,32)`, pooling, dense `2048→64→2`, input `[N,1,64,64]` float32 grayscale divided by 255, output two logits ordered `[benign, malware]`. The local `train/` data has 3,012 benign and 3,000 malware valid 256×256 grayscale PNGs. A stratified 70/15/15 split, five epochs, best-validation checkpoint and untouched 902-image test are recorded. `results/malware_cnn.pt` contains its trained state dict; `model_performance.pkl` records test accuracy **0.85144**, malware precision **0.91146**, recall **0.77778**, F1 **0.83933**, confusion matrix `[[418,34],[100,350]]`. The checkpoint is PyTorch, **not** an Android `.pte`; PNG provenance and any raw binary→image transformation are undocumented. Dependencies: PyTorch, Pillow, NumPy, scikit-learn, Matplotlib. Trained for this exact image representation, but **not yet mobile-deployable or a raw-file scanner**.
5. **`Phishing Classifier`** — Notebook `code/preprocess_and_combine_and_traintest.ipynb` merges URL sources, deduplicates URLs, extracts `[A-Za-z]+` tokens with NLTK `RegexpTokenizer`, applies English Snowball stemming, joins words, and uses default `CountVectorizer` to produce a **448,098-feature** sparse vector. It trains LogisticRegression, DecisionTree, and MultinomialNB with a stratified 80/20 split (`random_state=42`). Local-only pickles exist: `phishing_classifier_lr.pkl` (~3.6 MB), `phishing_classifier_dt.pkl` (~7.3 MB), `phishing_classifier_mnb.pkl` (~14.3 MB), `vectorization.pkl` (~7.5 MB); loaded object metadata confirms 448,098 expected features and labels `bad`, `good`. Notebook output reports LR accuracy **0.96680**, DT **0.96231**, MNB **0.96361**, with weighted precision/recall/F1 and confusion matrices. **Important evaluation flaw:** vocabulary is fit on all rows *before* splitting; thus these scores require a fresh leakage-safe holdout assessment. The pickles are not in GitHub and are not Android artifacts. Dependencies: pandas, NumPy, NLTK, scikit-learn, Matplotlib, Seaborn, wordcloud. Reproducible Python inference is plausible with the local vectorizer and stemmer resources; Kotlin parity is unproven. Candidate for first mobile detector.
6. **`Spam SMS Classifier`** — Notebook `code/sms-spam-detection.ipynb` merges two local CSVs, deduplicates, label-encodes `ham=0`, `spam=1`, lowercases, NLTK word-tokenizes, keeps alphanumeric tokens, removes English stopwords, applies Porter stemming, uses `TfidfVectorizer(max_features=3000)`, then **fits `MinMaxScaler` on all rows**, appends raw message character count, and produces `[N,3001]` features. It compares classifiers and saves a soft `VotingClassifier` of RandomForest, MultinomialNB, and ExtraTrees to local-only `model.pkl` (~12.8 MB), plus `vectorizer.pkl` (~94 KB). Notebook 80/20 stratified split (`random_state=2`) reports voting accuracy **0.98617** and spam precision **0.99237** on 1,446 rows; other outputs show individual classifiers. The scaler, stopword corpus/version, tokenizer resources, and feature-order manifest are **not saved**. TF-IDF/scaling are fit before the split, so the reported score may be optimistic. Python inference from just the two pickles is **not faithful** to training. Conversion of the ensemble and exact preprocessing is untested. Dependencies: pandas, NumPy, NLTK corpora, scikit-learn, Matplotlib, Seaborn, wordcloud. **Blocked pending preprocessing recovery**.

## 4. Missing artifacts and blockers

**P0:** SMS scaler and exact NLTK resource versions are absent. Do not ship its saved voting model until identical features can be rebuilt and Python/Android outputs match. Attempt recovery from the local training environment or deterministically reconstruct from the original dataset with recorded package versions; if exact recovery cannot be proven, request approval to retrain/replace the SMS pipeline.

**P0:** No DDoS or tabular malware model files. The historical notebook sessions are not exports. First look for original fitted artifacts elsewhere; if absent, request explicit approval before retraining those existing models.

**P0:** DDoS input is 78 flow values, while an Android non-root VPN provides packets requiring a full, correct bidirectional flow extractor. A feature availability/parity matrix must pass before DDoS classification is offered.

**P0:** Tabular malware needs a Windows PE parser reproducing 54 exact features. CNN needs documented binary-to-image provenance. Neither model detects Android malware behavior from its present inputs.

**P1:** Phishing and SMS `.pkl` files and local datasets are **not in GitHub**. Plan controlled artifact storage, licenses/provenance, signed versioning, and reproducible build handoff before a clean build is possible.

**P1:** No versioned feature schema, vocabulary/stopword hashes, calibration sets, release thresholds, or device parity corpus. Phishing and SMS vectorizers were fit before train/test split. DDoS's 99.95% row-split result needs independent temporal/source validation. CNN's 85.1% result is a single local held-out split, not mobile accuracy.

**P1:** No Llama weights, tokenizer, model-use approval/license record, quantized `.pte`, Android project, or on-device performance data.

## 5. Proposed technology stack and runtime choices

Use Kotlin, Compose/Material 3, Navigation Compose, Hilt, Coroutines/Flow, Room, Android Keystore where secret keys are needed, and the Android Storage Access Framework. Target arm64 phone builds; propose `minSdk 28`, `compileSdk/targetSdk 36`, subject to pinned runtime testing. Google Play currently requires Android 16/API 36 for new phone submissions [target API guidance](https://developer.android.com/google/play/requirements/target-sdk).

For converted scikit-learn candidates, choose ONNX Runtime Android CPU as first trial, not Python embedded in Android. ONNX Runtime documents Android Java support, CPU/XNNPACK execution, and model/operator trimming [ORT mobile guide](https://onnxruntime.ai/docs/tutorials/mobile/), [Android install](https://onnxruntime.ai/docs/install/). Assess `skl2onnx` supported ops for RF, LR, NB, voting outputs and any sparse/dense conversion; operator support is **not established** until conversion and device tests. For the trained PyTorch CNN, test ExecuTorch `.pte` export with XNNPACK; convolution/ReLU/pool/linear/dropout-in-eval are expected candidates, but actual export must verify the complete graph. For Llama, ExecuTorch is mandatory. LiteRT is relevant only for a recovered Keras dense artifact; none exists now. Android TensorFlow conversion is not assumed successful.

### Model integration gates

1. **Reference freeze:** pin Python package versions, hashes, artifact origin, exact inputs/outputs, corpus, score semantics, and expected labels. Keep existing fitted weights.
2. **Preprocessing parity:** Kotlin implementation must match Python at tokenizer tokens, stemmed tokens, vocabulary indices, IDF/scaler math, column order, dtype, missing/Inf behavior, image resize/interpolation, and channel order. Use golden files with boundary/Unicode/long/empty examples. Stop on unexplained mismatch.
3. **Conversion and operator audit:** export candidate, inspect graph and supported runtime ops, run desktop/mobile inference, compare original Python outputs within predeclared tolerances. Do not silently replace a failed estimator.
4. **Calibration and robustness:** evaluate on independent time/source/device partitions and out-of-distribution inputs. Fit calibration only on a separate calibration set, never on test data; otherwise display categorical results without confidence.
5. **Packaging:** signed model manifest with SHA-256, schema/tokenizer hashes, runtime version, model version, size, license, and compatibility range; atomically install/rollback. The app rejects corrupt or mismatched assets.
6. **Fallback:** model missing or parity failure yields **Unavailable** with safe static advice and manual alternative; never fabricate a result. Llama failure falls back to rule-based explanation.

## 6. Llama + ExecuTorch integration

**Candidate:** Meta Llama 3.2 1B Instruct on Arm CPU with ExecuTorch XNNPACK, because ExecuTorch documents Android `LlmModule`, `.pte` + tokenizer use, and a 1B export/quantization path [Android LLM runtime](https://docs.pytorch.org/executorch/stable/llm/run-on-android.html), [LLM export](https://docs.pytorch.org/executorch/stable/llm/export-llm.html). Keep the exported tokenizer, chat template, BOS/EOS IDs, and checkpoint from the **same** model revision. The Android AAR's Kotlin bindings are the default bridge; JNI is a contingency after API testing. Use a version-pinned 4-bit-weight `8da4w` candidate with KV cache; no `.pte` or conversion success exists today. Check Meta's [model license and access conditions](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct) before redistribution.

**Provisioning:** signed local asset pack or user-selected verified model pack. A development-time download is allowed; the installed app makes no inference call or telemetry request. A fully offline install path includes the app and pack on local media before airplane mode. The advisor is disabled until model/tokenizer integrity passes; other scanners still work. The Llama pack is expected to dominate storage/RAM, so do not load it at app startup. Treat ~0.5 GB 4-bit raw weights as a lower-bound calculation, not a shipping size; plan 0.8–1.5 GB pack/RAM ranges pending measurement, with KV cache and runtime additional. Benchmark a 6 GB reference phone and establish exclusion/fallback for lower-memory devices.

**Grounding:** structured finding and vetted remediation IDs only. The prompt labels SMS/URL/filename/network snippets as untrusted data, limits length, and instructs the model to quote only listed evidence IDs. Response schema: `summary`, `whySuspicious`, `possibleConsequences`, `safeActions[]`, `uncertainty`, `evidenceIds[]`. Validate schema, allowed actions, evidence references, and length; otherwise use rule text. Llama cannot operate permissions, delete files, send messages, open URLs, or change network settings. It may educate, but must distinguish a model prediction from confirmed compromise. Test prompt injections embedded in every raw input type.

**Performance contract:** measure cold load, first token, tokens/sec, peak PSS, thermal throttling, and battery on physical arm64 phones. Initial *targets*, not results: first token ≤10 s, ≥3 tokens/s, peak PSS ≤2.5 GiB on the chosen 6 GB device with a bounded prompt/context. Adjust targets only with measured user experience evidence.

## 7. Network monitoring feasibility

`VpnService` may observe traffic routed through its virtual interface after explicit user consent; the app must forward traffic safely through a proven userspace TCP/IP path or tunnel and stop on revocation. Forwarding through local sockets may require `INTERNET` permission in the VPN-enabled build, even though inference and advice remain offline; verify that no app-originated telemetry or cloud calls occur. It cannot capture arbitrary other apps' private files, decrypt TLS, see all non-routed traffic, or work alongside every other VPN. Use flow metadata rather than payload collection. The 78 DDoS features include durations, forward/backward packet lengths, inter-arrival times, header lengths, flags, active/idle statistics, and rates. A packet-to-feature feasibility matrix must classify each feature as reproducible, approximated, or unavailable; **approximations are not allowed for the existing model without revalidation**. Replay reference PCAPs through a CICFlowMeter-compatible extractor and the Android collector. A missing feature blocks classification. If the model is recovered/retrained with approval and parity passes, enable a foreground VPN service, explicit on/off control, visible notification, rate-limited alerts, and battery tests. Android requires foreground service type handling for recent targets [VpnService](https://developer.android.com/reference/android/net/VpnService), [FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types). The initial app can show monitoring as unavailable pending this gate.

## 8. Malware detection feasibility

The tabular dataset is Windows PE static metadata; it can support **user-selected PE file classification** if the exact 54-feature parser and fitted model are recovered. It cannot classify Android APK malware without an explicitly approved new dataset/model. The CNN expects PNG malware representations; because their generation from binaries is unknown, it cannot scan raw executables or the device. At most, a research/demo screen may classify user-selected PNGs with clear representation warnings after ExecuTorch parity. Use `ACTION_OPEN_DOCUMENT`, size/time bounds, safe parser libraries, no execution, no broad storage or package inventory permissions [Android SAF](https://developer.android.com/training/data-storage/shared/documents-files). A malware result should say “This selected Windows file/image resembles the training category,” never “Your phone is infected.”

## 9. App architecture, screens, and data

The module boundaries, Mermaid diagram, domain contracts, navigation graph, screen hierarchy, state model, and Room schema are specified in [`SYSTEM_ARCHITECTURE.md`](SYSTEM_ARCHITECTURE.md). In brief: Compose ViewModels invoke typed use cases; detection adapters produce structured findings; a policy engine supplies severity and safe actions; the advisor explains those findings; Room stores minimized event data; Flow updates dashboard/history; Hilt binds interfaces. The 13 requested screens are Splash, Onboarding, Permission Setup, Dashboard, URL Scanner, SMS Scanner, Network Monitor, Malware Scanner, Threat Details, Advisor, History, Settings, and Model Management. Every screen has loading/error/empty/model-missing states; permission-related screens also have denied/permanently denied states. Dark Material 3 design uses clear labels and accessible contrast, not an invented security score.

Room stores scan type/time/result/risk/model and preprocessing versions/non-sensitive indicator codes/user actions, monitoring sessions, model manifests, and retention settings. Default history excludes raw SMS, full URLs, packet payloads, and file bytes. Support delete single/all and a configurable retention period; test actual deletion and backup exclusion. Keystore protects encryption keys only where needed, with app-private storage and defined key-loss behavior.

## 10. Privacy, permissions, offline behavior, and notifications

- Initial app: manual paste/type and Android Share Sheet for URL/SMS. **No `READ_SMS`, `RECEIVE_SMS`, broad storage, or `QUERY_ALL_PACKAGES`**. Automatic SMS monitoring is a separately assessed product decision because Google Play restricts SMS permissions to eligible default handlers/approved exceptions [SMS policy](https://support.google.com/googleplay/android-developer/answer/16558241).
- Optional network monitor: `VpnService.prepare()` consent only when enabled; visible service and stop action; target-appropriate foreground service declaration. No root. If consent is denied or another VPN conflicts, manual scanners remain usable.
- Notification permission: request `POST_NOTIFICATIONS` on Android 13+ when alerts are enabled. Deduplicate, rate-limit, distinguish tentative findings, and never imply confirmation [notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).
- File scan: SAF picker only, validate content and bounds; URL scan never opens the URL. Sanitize log fields, no raw input in crash reports, no hidden analytics. The manual-scan build has no `INTERNET` permission; a VPN-enabled build may need it solely for disclosed traffic forwarding. Pin and hash all packaged assets, reject tampering; keep parser and tokenizer resource versions with the model.
- Fully offline verification: provision model pack locally, enable airplane mode, run URL/SMS/CNN supported scans and advisor, inspect app manifest and network logs, verify no attempted app-originated DNS/socket connections. The VPN build may forward the user's traffic when connectivity exists; distinguish that disclosed forwarding from cloud inference. Development downloads do not imply a runtime requirement.

## 11. Performance and resource budget

The **proposed targets** are manual URL/SMS p95 ≤500 ms after warmup, CNN p95 ≤2 s, dashboard cold start p95 ≤3 s without Llama load, advisor first token ≤10 s and ≥3 tokens/s, peak Llama process PSS ≤2.5 GiB on a 6 GB reference phone, VPN extra battery ≤5% over an 8-hour matched idle baseline, and alerts ≤1 duplicate per event window. These are release gates to measure and revise, **not achieved benchmarks**. Record AAB/APK size separately from locally provisioned model storage. Profile on at least two real Arm64 devices under cool and sustained conditions using Android Studio Profiler/Perfetto and battery tooling. Compare p50/p95, memory peaks, CPU, thermal state, startup, and long-running VPN overhead. The 1B model is the major size and RAM risk; load lazily and serialize advisory requests.

## 14. Testing and evaluation strategy

**Model:** Python baseline outputs vs Kotlin token/features and Android runtime outputs, class order, score tolerance, label parity, model loading, hash mismatch, quantization drift. Hold out data by source/time/family where feasible; report confusion matrices, per-class recall/precision, false positives, calibration only when fitted separately, and domain-shift behavior. Never treat historical notebook scores as shipping guarantees. For CNN, repeat the 902-image evaluation after export. For SMS, specifically detect scaler loss. For DDoS, replay PCAPs and compare all 78 feature values before evaluating classifier predictions.

**App:** unit tests for input validation, remediation policy, retention, score semantics, prompt schema/injection handling; instrumentation tests for navigation, Room migration/deletion, SAF, Share Sheet, permission denials, VPN revoke/restart, notification rate limits, airplane mode, model import/tamper/rollback, and process death. Accessibility tests cover TalkBack, large text, contrast, and reduced motion. Security tests include path traversal, decompression/image bombs, malformed PE files, overlong URLs/SMS, hostile prompt text, and absence of network traffic. Device benchmarks use two arm64 tiers, cold/warm, thermal and long-running scenarios; report actual measurements before release.

## 15. Risks and mitigations

| Risk | Mitigation / decision gate |
|---|---|
| Missing or incompatible fitted artifacts | Preserve existing weights; recover trusted original environment and metadata. Request explicit approval before retraining/replacement. Keep module unavailable if unresolved. |
| SMS preprocessing drift and feature leakage | Recover scaler, pin NLTK resources, use exact golden vectors and independent holdout. Do not ship a score if parity fails. |
| Phishing 448k feature memory/latency | Profile ONNX dense input and vocabulary; consider exact sparse linear/Naive Bayes evaluator from the same weights after parity proof. |
| DDoS false confidence from network flow mismatch | Mandatory 78-feature PCAP parity and cross-network validation; no verdict without proof. |
| Malware representation mismatch | Limit PE to selected Windows files and CNN to matching images; no APK/real-time claims. |
| Llama hallucination/prompt injection | Typed findings, untrusted delimiters, whitelisted evidence/actions, schema validator, rule fallback, adversarial tests. |
| Large Llama pack or thermal throttling | 1B quantized candidate, lazy load, bounded context, two-tier device benchmarks and low-memory fallback. |
| Privacy/permission/store policy | Manual SMS, SAF files, opt-in VPN, contextual notification permission, no internet/telemetry; review current Play rules before publication. |
| Malicious/corrupt model pack | Signed manifest and hash verification, private storage, atomic install, rollback, no arbitrary pickle on Android. |
